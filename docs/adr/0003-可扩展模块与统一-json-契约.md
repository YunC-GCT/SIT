# 可扩展模块与统一 JSON 契约

状态：accepted

本项目不把当前四个能力分组锁定为永久架构；建图、规划、路径后处理和运动控制只是当前模块边界，未来可以增加新的独立模块。所有模块之间统一使用 JSON 文件传递结构化数据，模块同时提供可单独调用的 Python API 和 CLI；顶层系统只负责按契约调度，不读取模块内部状态。整套流程遇到普通模块错误时保留运行批次、输出结构化错误并继续留在系统中，只有不安全运动或用户主动退出才终止整个系统。

## 采用理由

- 当前仓库没有需要保留的历史数据，因此直接重构契约，不增加旧 `.txt`、`.npy` 或旧目录结构的兼容分支。
- JSON 统一了人工检查、日志记录、跨语言读取和未来模块扩展的方式；数组和路径数据也必须定义稳定的 JSON 结构，而不是依赖 NumPy 的隐式形状。
- 错误留在运行批次中可以让研究者定位单个模块问题并重新执行，不必因规划器或预览器的一次失败重启整个系统。

## 必须避免的纰漏

- 不得让顶层 `main.py` 直接依赖任一模块的内部类或固定目录。
- 不得让模块通过全局变量、隐式当前工作目录或未记录的配置互相传递状态。
- 不得在模块失败后生成看似成功的 JSON；状态必须明确为 `failed`，下游必须拒绝未完成结果。
- 不得用“捕获异常后继续”掩盖错误；反馈必须包含模块、阶段、输入、原因和建议动作。
- 运动控制失败或退出时仍必须遵守先停车再退出，不能因为流程继续而让小车保持运动。

## 后果

统一 JSON 会增加数组序列化体积和模式设计工作，但换来了模块可替换、结果可审计和跨环境读取。若将来数据规模证明 JSON 不足，必须通过明确版本化的契约演进，而不是私下恢复模块间二进制耦合。
