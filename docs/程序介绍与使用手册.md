# SIT_LJGH_PROJECT 整体程序介绍与使用手册

> 本文描述当前实现的使用方式。模块通过统一 JSON 契约独立运行，顶层入口负责模式选择、批次调度、错误恢复和运动门禁。

## 一、程序做什么

本项目研究“地图图片 → 栅格地图 → 路径规划 → 路径后处理 → TurboPi 小车循迹”的完整流程。核心研究对象是 A*、Dijkstra、PRM、RRT、RRT* 等规划算法；小车控制只承担稳定、可观察的基本跟随，不追求厘米级精度。

实际运行环境为：Raspberry Pi 宿主机 Debian 12、`aarch64`，Docker 镜像 `turbopi:new`，容器内 Ubuntu 22.04.4、ROS2 Humble、Python 3.10.12。

## 二、整体设计

当前能力分为四个可扩展模块：

1. **地图处理**：读取图片、二值化、栅格化、选择起点和终点，输出带物理尺度的地图 JSON。
2. **路径规划**：在栅格地图上运行一个或多个算法，输出原始路径、随机种子和实验指标。
3. **路径后处理**：使用自研分段三次样条做基础平滑，再采样、碰撞复核和最大段长分解，输出控制器可执行的路径段。
4. **运动控制**：读取路径段，按“原地转向 → 零速过渡 → `linear.x` 前进 → 停止”控制 TurboPi。

这些是当前能力分组，不是永久固定的模块清单。新增定位、避障、里程计或其他研究内容时，应增加独立模块，通过 JSON 契约接入。

## 三、数据和运行批次

每次实验拥有独立的 `run_id`。运行目录保存各阶段的 JSON 输入、输出、参数、日志、预览和状态清单。

所有模块结果至少包含：

- `schema_version`
- `status`
- `module`
- `run_id`
- `inputs`
- `outputs`
- `parameters`
- `errors`
- 创建时间

地图坐标使用 `row/col`，地图上方为北、下方为南、左方为西、右方为东。物理距离使用米，速度使用 m/s，角速度使用 rad/s，时间使用秒。

## 四、普通模式使用流程

普通模式面向一次实车任务，减少不必要的输入：

1. 选择地图。交互终端中即使只有一张图片也会列出并询问编号，直接回车使用第一张；直接传图片路径或非交互模式不会询问。
2. 在地图窗口点击一次起点、一次终点。
3. 按 Enter 确认；R 重置，右键撤销，Esc 取消。
4. 使用配置中的默认栅格宽度和默认算法。
5. 系统完成规划、路径后处理和可视化。
6. 在路径预览中确认原始路径、平滑路径、执行段和预计时间。
7. 驱动前检查 `/cmd_vel`、底盘订阅者和其他发布者。
8. 用户确认后，按路径段执行 `turn` 模式。
9. 任务完成后选择重跑、更换算法、重新后处理、重新选点、切换地图或退出。

起点或终点落在障碍格时，系统要求重新选择，不会静默改点。

普通模式 CLI 示例：

```bash
python main.py map_pipeline/data/input/01_scattered.png \
  --headless --start 0,0 --goal 7,7 --no-drive
```

### 现场照片透视矫正

直接俯拍的照片通常包含透视、旋转、桌面背景和纸张接缝，直接栅格化会让地图范围和场景不一致。使用 `--rectify` 先做四点透视矫正和裁剪：

```bash
python main.py map_pipeline/data/input/图1.jpg \
  --headless --no-drive \
  --rectify \
  --corners "35,15;1225,15;1225,1420;35,1420" \
  --arena-width-m 2.0 \
  --grid-size-m 0.05 \
  --start 5,5 --goal 25,25
```

- `--corners` 是原图像素坐标，四个角点用 `;` 分隔；程序会自动排序为左上、右上、右下、左下。
- 不提供 `--corners` 时：有图形界面会打开四角点击窗口；只有终端时依次提示四个 `x,y`。
- `--arena-width-m` 给出场地真实宽度，程序按 `grid_size` 反算网格列数，并用真实宽度校准每个栅格的物理尺寸。
- `--grid-size-m` 覆盖配置中的栅格边长；例如 2 m 宽场地、5 cm 栅格 → 40 列。
- 矫正后的图片保存在运行目录的 `*_rectified.png`，结果 JSON 的 `outputs.rectification` 保存源角点、单应矩阵、输出尺寸和米/像素；`outputs.rectified_image` 指向矫正图。
- 纸张接缝、小噪点可以通过 `map_pipeline/config.yaml` 的 `min_obstacle_area_px` 和 `morphology_kernel` 清理。

使用 `--rectify` 时，`--start-px/--goal-px` 仍按原图像素坐标填写，程序会自动通过单应矩阵转换到矫正图；`--start/--goal` 则直接使用最终栅格坐标。

## 五、研究模式使用流程

研究模式用于算法实验，不默认驱动车：

1. 选择地图和起终点。
2. 选择多个规划算法或覆盖算法参数。
3. 为随机算法指定并记录随机种子。
4. 运行统一规划、路径后处理和指标统计。
5. 查看原始路径、平滑路径、分段路径和算法对比结果。
6. 将实验结果保存在独立运行批次中。

只有完成单独的驱动前安全确认后，研究结果才可以交给运动控制模块执行。

研究模式 CLI 示例：

```bash
python main.py map_pipeline/data/input/01_scattered.png \
  --mode research --headless --start 0,0 --goal 7,7 \
  --algorithms astar,dijkstra --seed 42
```

## 六、无显示器运行

无显示器时，使用命令行明确提供地图和起终点，不等待鼠标输入。预览保存到当前运行批次，缺少起点或终点时报告参数错误，不自动猜测。

支持三种方式：

1. 显式提供栅格坐标：

```bash
python main.py map.png --headless --start 2,2 --goal 37,37 --no-drive
```

2. 在终端输入起终点：

```bash
python main.py map.png --headless --select-terminal --no-drive
```

程序会先打印栅格行数、列数和栅格边长，并保存一张无起终点标记的预览图；随后依次提示输入 `起点 row,col` 和 `终点 row,col`。格式错误、越界、障碍格和起终点相同都会重新提示，直接回车取消。`--select-terminal` 要求 stdin 和 stdout 都是交互式终端。

3. 自动检测：有交互终端但未检测到图形显示时，主入口会自动切换到终端选点；如果 stdin/stdout 不是终端，则必须显式提供 `--start/--goal`，避免脚本挂起。

路径预览确认在无显示器时不再打开 OpenCV 窗口，而是打印预览图路径并要求输入 `yes` 接受；无人值守运行仍可使用 `--accept-path` 跳过该提示。任何无显示器驱动都必须额外使用 `--drive --accept-path --yes`（或在终端逐步确认）；默认只保存预览并跳过运动控制。

## 七、TurboPi 运动控制约定

- 速度话题：绝对 `/cmd_vel`
- 消息类型：`geometry_msgs/msg/Twist`
- 底盘节点：`/mecanum_chassis_node`
- `linear.x > 0`：前进；`linear.x < 0`：后退
- `angular.z > 0`：左转；`angular.z < 0`：右转
- 初始车头：地图正北
- 当前没有 `/odom`，使用 timer 和经验速度估算
- `linear.x=0.5` 持续约 1 秒约前进 0.30 m，仅作为初始经验标定

运动控制启动前应停止或隔离商家的 `gesture_control_node`、`object_tracking`、`line_following`、`avoidance_node` 和 `qrcode`，避免多个发布者竞争 `/cmd_vel`。

## 八、安全退出

所有退出路径都遵循：

```text
先重复发布零速度 Twist
→ 等待通信发送
→ 停止定时器和销毁节点
→ 只调用一次 rclpy.shutdown()
```

Ctrl+C、运行异常、路径完成和节点销毁都必须停车。没有 `/odom` 时不支持暂停后从中断点自动续跑。

## 九、错误处理

普通模块错误会暂停当前运行批次，并显示：

- 发生错误的模块和阶段
- 输入和输出位置
- 错误类型与原因
- 建议动作

交互模式用户可以重试、修改参数后重试、返回上一步或退出；任务完成后可重跑、换算法、重新后处理、重新选点、换地图或退出。每次重试使用批次内的版本化结果路径，已成功阶段不会被失败尝试覆盖。运动控制错误必须先停车。headless/批处理模式记录失败并返回非零状态，不启动后续运动。

## 十、开发与验收顺序

实现按本地票据的依赖顺序推进：

```text
01 契约基础
├── 02 地图处理
├── 03 规划器
└── 04 路径后处理
    └── 05 运动控制
        └── 06 顶层交互与恢复
            └── 07 全流程与实车验收
```

自动化测试优先使用模块 CLI、JSON 契约和 Fake ROS2 发布器；实车只做低速方向、转向、路径跟随和安全停车验收。实现细节、硬件边界和已确认的 ADR 见 `AGENTS.md`、`CONTEXT.md` 与 `docs/agents/`。
