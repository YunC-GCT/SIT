# TurboPi 麦轮小车硬件与运动控制资料

本文是 TurboPi 相关开发的硬件参考和实现边界。涉及 `motion_control/`、ROS2 速度指令、麦轮逆运动学、里程计、行驶距离、电机或舵机时，先核对本文。

本文中的产品与部件参数来自项目方提供的资料，尚未由仓库内测试或厂家原始文档独立验证。需要影响实车安全或控制精度的数值时，以实测结果为准。

## 实际部署环境

根据树莓派宿主机和 `turbopi` 容器中的实际查询结果，当前实车部署环境已确认如下：

- 宿主机是小车上的 Raspberry Pi，运行 Debian GNU/Linux 12（Bookworm，Raspberry Pi 内核 `6.12.25+rpt-rpi-2712`）。宿主机不是 Ubuntu。
- 宿主机 CPU 架构为 `aarch64`（64 位 ARM）。
- 项目源代码位于宿主机的 `/home/pi/SIT_LJGH_PROJECT`。
- 代码通过 Docker 容器运行，容器名为 `turbopi`。
- 容器镜像为 `turbopi:new`，当前状态为 `running`。
- 容器内运行 Ubuntu 22.04.4 LTS（Jammy Jellyfish）。
- 容器内 CPU 架构同样为 `aarch64`。
- 容器内 ROS2 发行版为 Humble，命令位于 `/opt/ros/humble/bin/ros2`。
- 容器内 Python 版本为 3.10.12。
- 使用 `docker cp /home/pi/SIT_LJGH_PROJECT turbopi:/home/ubuntu/` 将项目从树莓派宿主机复制到容器内的 `/home/ubuntu/`。
- 进入容器终端后，在容器内的 Ubuntu 用户目录下运行项目；通常项目路径为 `/home/ubuntu/SIT_LJGH_PROJECT`。
- ROS2、Python 依赖以及底盘通信环境应以容器内安装和配置为准，不能只检查宿主机。
- 已确认 `turbopi` 容器可以访问真实底盘，商家提供的示例代码已在该环境中成功驱动小车。
- 实际操作流程是先进入可弹出的虚拟机/小车终端，再执行宿主机 Docker 命令并进入 `turbopi` 容器；容器自动启动不是项目约束。
- 已确认底盘节点为 `/mecanum_chassis_node`，订阅绝对话题 `/cmd_vel`（`geometry_msgs/msg/Twist`）。相对话题 `cmd_vel` 在根命名空间下当前未发现，不得把两者混用。
- 已确认当前系统没有 `/odom`、编码器或关节状态话题，只有 `/ros_robot_controller/imu_raw`（`sensor_msgs/msg/Imu`）。IMU 不能单独替代平移里程计，因此当前项目的精确位移闭环尚未具备。
- 查询时发现 `gesture_control_node`、`object_tracking`、`line_following`、`avoidance_node` 和 `qrcode` 同时向 `/cmd_vel` 发布，底盘只有一个订阅者。路径控制运行前必须停用这些会发布速度的功能节点，或建立明确的控制仲裁，否则多个发布者会互相覆盖指令。
- 根据 `car_move_demo.py` 的实车观察，`linear.x = 0.5` 持续约 1 秒时，小车前进约 30 cm。当前可暂记为经验标定：指令值 `0.5` 对应有效前进速度约 `0.30 m/s`，有效速度系数约 `0.60`（实际/指令）。该数据的负载、电池电量、地面、启动延迟和测量误差尚未记录，不能直接视为所有方向、所有速度下的固定比例。

推荐的部署检查顺序是：

```bash
# 在树莓派宿主机执行
docker cp /home/pi/SIT_LJGH_PROJECT turbopi:/home/ubuntu/
docker exec -it turbopi bash

# 在 turbopi 容器内执行
cd /home/ubuntu/SIT_LJGH_PROJECT
python3 --version
printenv ROS_DISTRO
ros2 topic list
```

这条 `docker cp` 命令表达的是“从宿主机复制到已有容器”，不是构建镜像，也不是把容器内改动自动同步回宿主机。修改代码后若仍使用这种工作流，需要重新复制；容器内产生的结果文件也不会自动回写到宿主机项目目录。

### 目前仍需确认的环境事实

以下内容目前仍需在 `turbopi` 容器内进一步核对，涉及运行或调试时不能仅凭操作系统版本推断：

- ROS2 Humble 是否在每次新终端中自动 source `/opt/ros/humble/setup.bash`
- `numpy`、`opencv-python`、`pyyaml`、ROS2 Python 包是否完整安装
- 容器是否映射了 `/dev`、网络、USB、串口或其他底盘设备
- ROS2 初始化脚本中引用的 `/home/ubuntu/setup.sh` 当前不存在；需要确认这是容器 shell 配置遗留，还是每次加载环境都会触发的问题

因此，后续 agent 执行项目命令时，应优先说明命令是在“树莓派宿主机”还是“`turbopi` 容器内”执行；ROS2 节点、Python 程序和话题调试默认在容器内进行。

## 当前软件契约

- 本仓库的运动控制层发布 ROS2 `/cmd_vel`，消息类型为 `Twist`。
- `linear.x`、`linear.y` 表示底盘坐标系中的平移速度，`angular.z` 表示绕 Z 轴的角速度。
- 当前 mecanum 模式直接发布 `(vx, vy)`，并保持 `angular.z = 0`；当前仓库不直接输出四个电机的转速或 PWM。
- 四轮速度逆解若已由 TurboPi 底盘驱动节点完成，本仓库应继续发布底盘级 `Twist`，避免重复逆解。
- 路径每一格的目标物理距离来自 `grid_map.npz` 中的 `grid_size`。当前代码优先使用 odom 实际位移判断到达，并以理论时间作为兜底。
- 坐标方向和初始朝向以运行配置及实际底盘坐标系为准。修改符号映射前，应通过低速单方向测试确认前进、后退、左移和右移。

## 安全退出与停车契约

商家示例的退出设计体现了必须保留的安全目标：收到 `Ctrl+C` 或 `SIGINT` 后先发布零值 `Twist`，让底盘停止，再关闭 ROS2。示例中 `stop()` 会调用 `rclpy.shutdown()`，而 `main()` 的 `finally` 又再次调用一次；因此实际退出时可能出现 `RuntimeError: Context must be initialized before it can be shutdown`。这个异常说明 shutdown 调用了两次，不代表应移除停车逻辑。

本项目后续实现必须满足以下顺序和性质：

1. 任何退出路径（`Ctrl+C`、`SIGINT`、运行异常、路径完成或节点销毁）都先执行停车动作。
2. 停车动作至少发布零速度 `Twist`；实车默认沿用重复发布零速并留出通信缓冲的策略。
3. 停车动作不应依赖 ROS2 shutdown 的返回结果；即使 shutdown 已执行或抛出“已关闭”类异常，也要保证零速发布已经完成。
4. shutdown 必须幂等：信号处理函数、`except KeyboardInterrupt` 和 `finally` 不能无条件重复关闭同一个 ROS2 context。可通过统一的 `shutdown_once()`、上下文状态判断或捕获已关闭异常实现。
5. 停车和 shutdown 的异常处理不能掩盖原始故障，也不能让程序在已发送停车命令后继续发布运动命令。

验证退出逻辑时，应检查两件独立的事：`/cmd_vel` 上确实出现零速度消息，以及进程最终正常退出或只报告可解释的关闭异常。不能只以“没有 traceback”作为安全停车证明。

## 商家示例代码分析

参考文件位于开发机桌面：

- `car_forward_demo.py`
- `car_move_demo.py`
- `car_slant_demo.py`
- `car_turn_demo.py`
- `car_drifting_demo.py`

这些文件是底盘接口的行为参考，不是本仓库的自动化测试，也不是距离控制实现。它们共同采用 `rclpy`、`geometry_msgs.msg.Twist` 和 ROS2 定时器：创建节点后建立底盘发布器，每次定时回调发布当前动作，收到 Ctrl+C 时发布零值 `Twist` 并关闭 ROS2。

### 动作与 Twist 映射

| 示例 | 线速度与角速度 | 参考含义 |
| --- | --- | --- |
| 前进 | `linear.x = 0.5`，其余分量为 0 | 沿底盘 X 正方向前进 |
| 前后左右 | `(linear.x, linear.y)` 依次为 `(0.5, 0)`、`(-0.5, 0)`、`(0, 0.5)`、`(0, -0.5)` | 四个正交平移方向 |
| 斜向 | `linear.x` 与 `linear.y` 同时取 `+/-0.5` | 对角线平移；两个分量同时生效 |
| 原地转向 | `angular.z = 5.0` 或 `-5.0` | 左右旋转；平移分量应为 0 |
| 漂移 | `linear.y = -0.2, angular.z = 0.5` 或相反符号 | 横移与自转同时发生 |

示例默认发布话题名写作 `cmd_vel`，本仓库的代码也使用相对话题名 `cmd_vel`，而 README 以 `/cmd_vel` 表示目标接口。ROS2 中相对名称会受节点命名空间影响，可能解析为不同的实际话题；接入前必须用 `ros2 topic list` 和 `ros2 topic info` 确认底盘驱动实际监听的名称，不要只凭代码字符串判断。

示例动作的速度值是演示值，不是 TurboPi 的通用标定值。它们没有提供轮径、轮距、轴距、编码器换算或“运行 N 秒等于多少米”的依据，因此不能直接用来替换本仓库的 `grid_size`、odom 闭环或距离估算参数。

### 定时器和状态机约定

- `car_forward_demo.py` 每 1 秒重复发布前进命令。
- `car_move_demo.py` 每 1 秒在四个正交方向之间循环切换。
- `car_slant_demo.py` 每 1 秒在四个斜向组合之间循环切换，初始化时额外等待约 1 秒。
- `car_turn_demo.py` 每 1 秒在正负旋转角速度之间循环切换。
- `car_drifting_demo.py` 每 3 秒在两组横移加旋转命令之间切换。

这是一种“定时发布 + 状态切换”的演示模型：回调只改变动作状态，不根据 odom 判断距离，也没有动作结束后的显式停顿。路径循迹不能直接照搬这种切换方式，应由路径段、目标位移和 odom 到位条件驱动状态转换。

### 示例中的实现风险

- 示例复用一个可变的 `Twist` 对象。新增动作状态时若没有显式清零未使用的 `linear`/`angular` 分量，前一状态可能残留到后一状态；本仓库应优先为每次发布构造全新的零值 `Twist`，再写入需要的分量。
- 示例的停止处理只发布一次零速度。实车控制应沿用本仓库的安全停车策略：重复发布零速度并留出通信缓冲，然后销毁节点。
- 示例没有限制速度、加速度或动作持续时间，且旋转示例使用 `angular.z = 5.0`，不应未经低速验证直接用于实车。
- 发布器队列深度为 1，适合演示当前状态，不等于路径控制的可靠传输或反馈机制。
- `time.sleep(1)` 放在节点初始化中只是等待底盘连接的简单做法；正式代码应使用可观察的连接/话题状态，不要把固定睡眠当成设备就绪证明。

### 后续仿真与实车验证顺序

实现或修改动作映射时，先用与示例相同的单动作命令验证接口：前进、后退、左移、右移、斜移、原地左转、原地右转。每项只使用低速和短时发布，并记录实际方向、`/cmd_vel` 话题、`/odom` 响应及停止是否生效；确认通过后再接入路径段状态机。漂移属于平移与旋转耦合动作，当前路径循迹默认不使用，除非需求明确要求。

## 麦克纳姆轮运动学

轮组资料描述为 ABAB 组合，A、B 轮互为镜像，辊子轴与轮毂轴夹角为 45 度。

符号约定：

- `Vx`：底盘沿 X 轴的平移速度
- `Vy`：底盘沿 Y 轴的平移速度
- `Vw`：底盘绕 Z 轴的角速度
- `L`：左右车轮轮心间距，即轮距
- `H`：前后车轮轮心间距，即轴距
- `VA`、`VB`、`VC`、`VD`：四个麦轮的轮缘线速度

项目方提供的逆运动学关系为：

```text
R = L / 2 + H / 2

VA = Vx - Vy - Vw * R
VB = Vx + Vy + Vw * R
VC = Vx - Vy - Vw * R
VD = Vx + Vy + Vw * R
```

这些公式只有在轮位编号、各轮正转方向、底盘 X/Y 轴方向和 ABAB 安装顺序完全一致时才成立。当前资料未给出 A/B/C/D 对应的具体轮位，而且 `VA = VC`、`VB = VD` 的形式需要结合底盘接线与驱动实现复核。将公式写入电机控制代码前，必须完成四轮悬空测试和低速落地测试，并记录每个正指令对应的实际轮向。

若驱动接口需要角速度而不是轮缘线速度，使用：

```text
wheel_angular_speed_rad_s = wheel_linear_speed_m_s / wheel_radius_m
wheel_speed_rpm = wheel_angular_speed_rad_s * 60 / (2 * pi)
```

## 距离与时间推算

### 当前经验标定

在 `car_move_demo.py` 的测试条件下：

```text
linear.x = 0.5
持续时间 ~= 1.0 s
实测前进距离 ~= 0.30 m
实测有效速度 ~= 0.30 m/s
```

因此在没有 `/odom` 时，可以把 `0.30 m/s` 作为临时的前进方向 timer 估算值；不要把 `linear.x` 数值直接当作已经标定的米每秒。该标定至少应在相同电池电量、地面和负载下重复 3 次，并分别测量 `linear.x`、`linear.y` 以及不同速度值，再用于更新配置。横移和旋转不能沿用前进标定值。

已知轮径 `D` 和减速箱输出轴转速 `n`（RPM）时，理想轮缘速度为：

```text
wheel_linear_speed_m_s = pi * D_m * n_rpm / 60
```

已知输出轴累计圈数 `N` 时，理想行驶距离为：

```text
distance_m = pi * D_m * N
```

仅进行开环时间估算时：

```text
distance_m ~= commanded_chassis_speed_m_s * elapsed_time_s
elapsed_time_s ~= target_distance_m / commanded_chassis_speed_m_s
```

开环结果会受到负载、电池电压、地面摩擦、麦轮横向滑移、加减速过程和电机个体差异影响，只能作为超时兜底。当前项目的段完成判断应继续以 odom 位移为主。

### 尚缺的标定数据

现有资料不足以把 PWM、电机电压或标称 RPM 可靠换算为实车行驶距离。实现此类换算前，需要补齐并记录：

- 麦轮有效直径或滚动周长
- 实际轮距 `L` 与轴距 `H`
- A/B/C/D 与左前、右前、左后、右后的对应关系
- 每个电机正转方向与驱动通道映射
- 编码器每圈计数；若硬件没有编码器，应明确记录
- PWM 或速度命令到负载转速的实测标定曲线
- `/odom` 的来源、单位、坐标系和更新频率
- 纵向、横向与旋转运动的系统误差和滑移修正系数

这些数据未补齐前，使用 odom 做闭环反馈，并把额定转速计算结果标记为理论估算，不作为精确到达依据。

## 实车调试边界

- 首次验证使用架空车轮或低速、开阔场地，并准备立即停止底盘。
- 一次只验证一个自由度：先 `Vx`，再 `Vy`，最后 `Vw`。
- 每次记录命令、轮向、odom 位移和实际位移，确认符号与单位后再提高速度。
- 舵机 PWM 必须限制在 500-2500 us，电机和舵机供电保持在各自额定范围内。
- 堵转参数描述的是极限工况和保护能力，不是允许持续运行的工作点。
